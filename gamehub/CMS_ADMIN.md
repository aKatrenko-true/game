# GameHub CMS — редактор сайта

Страница редактора: `/admin/cms`. Используется тот же пароль, что и для `/admin` (`ADMIN_PASSWORD` в переменных окружения Render).

## Возможности
- Создание, редактирование, сортировка, скрытие и удаление разделов.
- Типы блоков: `hero`, `content`, `cards`, `players`, `teams`, `matches`, `gallery`, `custom`.
- Текст, изображение, видимость и порядок для каждого раздела.
- Настройки названия сайта, логотипа, SEO-описания, цветов и подписей меню.
- Публичный API `GET /api/cms/content` возвращает настройки и разделы для отрисовки.
- Все операции редактирования требуют заголовок `X-Admin-Password`; публичное чтение CMS не требует авторизации.

## Изображения
В текущем редакторе файл до 1,5 МБ читается браузером как data URL. Выберите нужный раздел во вкладке «Изображения» и нажмите «Сохранить изображение в раздел» — редактор сохранит изображение в выбранный раздел автоматически. Для рабочего production-сайта предпочтительно подключить объектное хранилище (S3-compatible/Cloudinary) и хранить в PostgreSQL только URL: data URL раздувает размер записей и резервных копий.

## Важные ограничения первой версии
- Не все существующие блоки и элементы главной страницы имеют отдельные настройки CMS; пока подключены основные настройки, главный экран, пользовательские контентные блоки и часть видимости.
- Типы `players`, `teams` и `matches` описывают блоки, но не создают новую бизнес-логику. Новые программные функции и новые типы данных по-прежнему требуют кода.
- Нет отдельной системы черновиков/публикации, версионирования и отката изменений.
- Нет автоматического резервного копирования медиа.
- До выкладки требуется проверить Python-компиляцию, миграцию PostgreSQL и SQLite, доступ администратора/неавторизованного клиента, мобильную верстку и сохранение/отображение после перезагрузки.

## Автоматические проверки в проекте

GitHub Actions запускает проверки при push и pull request, если меняются файлы `gamehub/**` или workflow:
- `python -m compileall -q app.py tests` — компиляция приложения и тестов Python.
- `node --check` для `app.js`, `cms.js`, `cms-public.js` и `lfg.js` — синтаксис клиентского JavaScript.
- `pytest` — API, авторизация администратора, создание/изменение/удаление CMS-разделов, валидация slug и настроек, проверка скрытого контента, сохранение настроек и медиа после повторной инициализации БД, HTTP smoke-проверки страниц и статических файлов.
- Отдельная PostgreSQL job проверяет схему, миграционную/повторную инициализацию, API и сохранение CMS-настроек/медиа в PostgreSQL.
- Frontend contract tests проверяют, что CMS-видимость применяется к desktop/mobile-навигации и CTA, SPA не открывает скрытый раздел, контент добавляется через `textContent`, а редактор содержит разделы, оформление и медиатеку.
- Playwright запускает Chromium и проверяет главную страницу в мобильном viewport, отсутствие ошибок JavaScript, доступность мобильной навигации, скрытие пунктов игроков/команд/матчей на desktop и mobile, а также блокировку перехода на скрытый SPA-раздел.

## Ручной smoke-check перед публикацией

Эти проверки требуют работающего браузера и целевого окружения; они не считаются пройденными автоматически только на основании CI.

1. Войти в `/admin/cms` с `ADMIN_PASSWORD`; убедиться, что неверный пароль не открывает редактор.
2. Создать раздел с уникальным slug, изменить заголовок/текст/порядок, сохранить и обновить страницу.
3. Скрыть по очереди блоки игроков, команд и матчей: проверить desktop-меню, мобильное меню, CTA и прямую попытку открыть скрытый SPA-раздел. Вернуть видимость и проверить обратное поведение.
4. Во вкладке «Изображения» загрузить PNG/JPG/WebP/GIF/SVG размером до 1,5 МБ; проверить предпросмотр, сохранение, отображение и повторное открытие после обновления. Отдельно проверить отказ для файла больше лимита и неподдерживаемого типа.
5. Изменить название сайта, логотип, SEO, подписи меню и HEX-цвета; обновить главную и проверить применение. Попробовать некорректный цвет и неизвестный ключ через API — запрос должен быть отклонён.
6. Проверить `/api/cms/content`: скрытые разделы не должны отдавать текст/изображение, а внутренние настройки — попадать в публичный ответ.
7. Повторить сценарии в узком мобильном viewport и на реальном телефоне: горизонтальная прокрутка, перекрытие контента мобильной навигацией, доступность кнопок и формы редактора.
8. Перезапустить тестовый сервис с той же БД и убедиться, что разделы/настройки/изображения сохранены. После успешного smoke-check отдельно проверить health endpoint и логи целевого окружения.

Не отмечайте ручные проверки как пройденные, пока они фактически не выполнены в браузере и на целевом окружении.
