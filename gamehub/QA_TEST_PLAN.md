# Краткий тест-план GameHub

Подробные сценарии находятся в [тест-кейсах](qa-project/TEST_CASES.md), матрица связей — в [трассировке](qa-project/TRACEABILITY.md), а результаты прогонов фиксируются в [шаблоне отчёта](qa-project/TEST_RUN_TEMPLATE.md).

## Что известно на текущий момент

- Пользователь подтвердил, что после исправления JavaScript-селектора каталог игроков снова отображается.
- Пользователь сообщал, что новые записи сохраняются; отдельный свежий отчёт с шагами и результатами не оформлен.
- В текущем `master` `gamehub/app.py` использует SQLite. Путь к файлу задаётся через `GAMEHUB_DB`; при отсутствии переменной используется `gamehub/gamehub.db`.
- Скриншоты PostgreSQL/Render относятся к историческому развёртыванию другой ветки. Текущую конфигурацию опубликованного сайта нужно проверять отдельно.
- В коде есть API для игроков, команд, матчей, аккаунтов, LFG и административных операций. Наличие маршрута не подтверждает, что соответствующая форма реализована в интерфейсе или что проверка пройдена.
- Историческая ошибка Service Worker требует повторного тестирования.
- Полный регрессионный прогон не оформлен.

## Автоматические тесты

В `gamehub/tests/test_api.py` есть тесты для health, списка и создания игроков, дубликатов, валидации никнейма, поиска, запрета матча команды против самой себя и нескольких сценариев LFG.

Это описание состава тестов, а не результат последнего запуска. Статус выполнения следует указывать только после получения результата `pytest -q` или GitHub Actions на конкретном commit.

## Порядок проверки

1. Зафиксировать ветку, commit и окружение сайта.
2. Получить результат API-тестов и сохранить ссылку на запуск.
3. Проверить API и основные сценарии интерфейса.
4. Проверить авторизацию LFG и административные маршруты.
5. Выполнить проверки Service Worker, адаптивности и клавиатурной навигации.
6. Обновить статусы кейсов и матрицу трассировки по фактическим результатам.
