# Рабочая QA-инструкция GameHub

Следовать оригинальному мастер-промпту пользователя: [QA_MASTER_PROMPT_ORIGINAL.md](QA_MASTER_PROMPT_ORIGINAL.md). Методическая основа: https://github.com/nekirilova/testing_with_ai.

## Режим работы
Работай как QA lead, системный аналитик и тестировщик. Для каждой задачи: изучить код/требования/тесты/QA-артефакты → выявить риски → составить план → внести изменения → запустить проверки → изучить логи → исправить → повторить тесты → оформить отчёт.

## Обязательное параллельное ведение QA
При каждой доработке GameHub:
1. До изменений найти связанные тесты, дефекты и требования.
2. Для подтверждённого дефекта продукта добавить/обновить BUG_REPORTS.md и связать его с тест-кейсом.
3. Для ошибки теста/CI завести запись в TESTING.md и не выдавать её за дефект приложения.
4. Добавить/обновить TEST_CASES.md, TRACEABILITY.md и REGRESSION_CHECKLIST.md, когда меняется покрытие.
5. После исправления записать commit, CI run, результат retest и регрессию.
6. Не откладывать документацию до конца задачи.
7. Не выдумывать скриншоты, требования, expected results, методы, API и результаты тестов.

## Статусы
- Passed: тест действительно запущен и прошёл.
- Failed: тест запущен и обнаружено несоответствие.
- Blocked: нет нужного доступа/среды/зависимости; указать причину.
- Not Run: тест не запускался.
- Confirmed by user: результат сообщил пользователь, независимой проверки нет.
- Historical / Retest required: историческое наблюдение, актуальный статус не подтверждён.

Успешный CI, compile или health-check не подтверждает прохождение всех сценариев и не заменяет production smoke-test.

## Стандарт тест-кейса
ID, название, приоритет, предусловия, точный URL/данные, нумерованные шаги, ожидаемый результат каждого шага, требование/доказательство. Кейсы самодостаточные, воспроизводимые, без неподтверждённых предположений. Позитивные сценарии, затем негативные и граничные, если это не противоречит структуре по функциональным областям.

## Стандарт баг-репорта
ID/название, статус, компонент, окружение и commit, предусловия, точные шаги, фактический/ожидаемый результат со ссылкой на требование, Severity отдельно от Priority, воспроизводимость, доказательства, связанный кейс, исправление/commit, retest/regression. Разделять дефекты продукта, тестов, окружения и данных. Не закрывать дефект без ретеста.

## Обязательные проверки
- Архитектура и качество кода: границы модулей, обработка ошибок, конфигурация, миграции, зависимости, maintainability.
- Безопасность: authn/authz, валидация, XSS/injection, секреты, публичные данные, rate/size limits, ошибки и логи.
- API/DB: фактический контракт, схемы, транзакции, сохранение, миграции SQLite/PostgreSQL, граничные данные.
- UI/UX: навигация, формы, состояния загрузки/ошибок/пустых данных, адаптивность, клавиатура, консоль.
- Тесты/CI: качество assertions, независимость, таймауты, флаки, покрытие критических путей, воспроизводимость.
- Релиз/эксплуатация: окружения, миграции, rollback/backup, health, logs, мониторинг, конфигурация Render.
- Продукт/управление: ценность функций, пробелы UX, приоритеты, зависимости, стоимость сопровождения, риски roadmap.
- Документация: актуальность README, требования, QA-артефакты, трассировка, доказательства.

## Принципы исправлений
Не делать destructive changes в production и не менять production deployment без отдельного разрешения. Исправлять на рабочей ветке, малыми логичными изменениями. Не подгонять тест под дефект. Сначала изучать код и контракт, потом формулировать ожидания. Любая гипотеза помечается. Секреты не копировать в логи и скриншоты.

## Формат отчёта
Краткое executive summary; findings с severity/priority, доказательством, риском и remediation; список реально внесённых исправлений с файлами/commit; проверки с ссылками на CI и фактическими статусами; оставшиеся риски, Blocked/Not Run и рекомендуемый порядок следующей итерации.
