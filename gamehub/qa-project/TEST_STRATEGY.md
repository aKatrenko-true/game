# Стратегия тестирования GameHub

## 1. Цель
Проверить, что пользователи могут просматривать игроков, искать напарников, изучать команды и матчи, а интерфейс остаётся работоспособным на мобильных устройствах и компьютерах. Выявлять дефекты до публикации изменений.

## 2. Объект тестирования
- Frontend: HTML, CSS, JavaScript, адаптивная навигация, карточки игр, каталоги, формы.
- Backend: FastAPI REST API.
- Хранилище: SQLite.
- PWA: manifest, service worker, обновление ресурсов и поведение при сетевых сбоях.
- Административная часть и личный кабинет — отдельный расширяемый контур; для функций с авторизацией особенно важны права доступа и защита данных.

## 3. Область проверки
**Входит:** функциональные проверки, API, позитивные и негативные сценарии, граничные значения, регрессия, responsive UI, базовая доступность, консоль браузера, сетевые запросы, обработка ошибок и smoke-тестирование деплоя.

**Не считается подтверждённым без отдельного запуска:** нагрузочное тестирование, полноценный аудит безопасности, кросс-браузерная матрица, доступность по WCAG, проверка установки PWA на реальных iOS/Android устройствах.

## 4. Приоритеты
- **P0 — критический:** приложение недоступно, данные пользователей раскрываются/теряются, обход авторизации.
- **P1 — высокий:** ключевой пользовательский сценарий сломан (каталог, создание профиля, авторизация/администрирование).
- **P2 — средний:** существенная функция работает некорректно, но есть обходной путь.
- **P3 — низкий:** косметические дефекты, незначительные несоответствия.

## 5. Виды тестирования
| Вид | Что проверяем | Подход |
|---|---|---|
| Smoke | главная, API health, каталоги | короткий набор после деплоя |
| Functional | поиск, фильтры, формы, переходы | ручные тест-кейсы |
| API | методы, статусы, схемы, ошибки | pytest + httpx, Swagger/Postman |
| Validation | обязательность, длины, форматы, дубликаты | граничные и негативные значения |
| Regression | существующие сценарии после изменений | чек-лист регрессии |
| Responsive | 360 px, 390 px, планшет, desktop | DevTools и реальные устройства |
| PWA | установка, кэш, обновление версии, offline fallback | браузерные инструменты |
| Security basics | авторизация, права, секреты, ввод данных | безопасные проверки на собственном стенде |
| Accessibility basics | фокус, подписи, контраст, клавиатура | ручная проверка |

## 6. Окружение
- Production/demo: https://gamehub-055p.onrender.com
- Local: Windows, Python, FastAPI, SQLite; запуск по README приложения.
- Браузеры для первичного smoke: Chrome desktop; далее Chrome Android и Safari iOS.
- Для API: Swagger UI, pytest/httpx; Postman — дополнительный ручной инструмент.

## 7. Тестовые данные
Использовать демонстрационные никнеймы и уникальные данные для каждого прогона. Не применять реальные пароли/почту. Проверять CS2, WarDogs, Valorant, Apex Legends и Dota 2 там, где они поддерживаются приложением. При проверке создания сущностей учитывать, что данные могут сохраняться в общей базе стенда.

## 8. Критерии начала
- Версия/коммит известны.
- Стенд отвечает на `/api/health`.
- Определены требования и ожидаемые результаты.
- Подготовлены тестовые данные.

## 9. Критерии завершения
- Выполнены согласованные P0/P1 сценарии.
- Нет открытых дефектов P0; риски P1 явно согласованы.
- Пройден smoke и регрессия затронутых областей.
- Все результаты и известные ограничения зафиксированы.
- «Пройдено» ставится только после фактического выполнения.

## 10. Риски
- Бесплатный хостинг может засыпать и медленно отвечать после простоя.
- SQLite на облачном окружении может быть непостоянной без отдельного persistent disk.
- Service worker может показывать устаревшие файлы.
- Общий публичный стенд содержит демонстрационные данные; проверочные записи нужно отличать от реальных.
- Административные операции требуют строгой проверки авторизации и контроля доступа.

## 11. Отчётность
На каждый прогон фиксировать дату, версию/commit, окружение, ID теста, фактический результат, статус (Pass/Fail/Blocked/Not Run), ссылку на баг и доказательство.
