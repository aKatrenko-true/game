# Стратегия тестирования GameHub

## Цель

Проверить основные пользовательские сценарии сайта GameHub, корректность API и сохранения данных, а также не считать известные проблемы исправленными без повторной проверки.

## Объект тестирования

GameHub — веб-сайт с каталогом игроков, командами, матчами, поиском команды (LFG) и административной панелью.

- Backend: FastAPI, файл `gamehub/app.py`.
- Frontend: HTML, CSS и JavaScript в `gamehub/static/`.
- База данных в текущем `master`: SQLite. Файл задаётся через `GAMEHUB_DB` или используется `gamehub/gamehub.db`.
- API-автотесты: `gamehub/tests/test_api.py`.
- CI: workflow в `.github/workflows/gamehub-tests.yml`.

Эти сведения относятся к коду ветки `master`. Они не подтверждают автоматически, какая версия и база данных сейчас используются опубликованным сайтом.

## Области проверки

| Область | Что проверять | Приоритет |
|---|---|---|
| Доступность и API | Главная, health, списки игроков, команд и матчей | P1 |
| Каталог игроков | Загрузка списка, поиск, фильтры, пустое состояние | P1 |
| Создание профиля | Валидация, создание, дубликаты, сохранение после обновления | P1 |
| Команды и матчи | Получение списков, фильтрация, API создания и изменения | P1 |
| LFG | Список и фильтры, авторизация, валидация, права владельца объявления | P1 |
| Административный API | Отсутствующий и неверный пароль, успешный доступ, операции с данными | P0 |
| База данных и деплой | Фактический commit опубликованного сайта, используемая база, сохранение записей | P1 |
| Service Worker | Регистрация, cache, обновление ресурсов, отсутствие необработанных ошибок | P1 |
| Адаптивность и доступность | Основные размеры экрана, фокус и управление клавиатурой | P1/P2 |

## Что важно учитывать при проверке

- Страница `/admin` отдаёт HTML. Это не проверка доступа к административным данным: проверять нужно API `/api/admin/*`.
- Административный API использует общий пароль из `ADMIN_PASSWORD`, передаваемый в заголовке `X-Admin-Password`. При отсутствии настройки ожидается HTTP 503, при неверном или отсутствующем пароле — HTTP 401.
- Создание LFG без авторизации должно возвращать HTTP 401; попытка изменить чужое объявление — HTTP 403.
- Наличие API-маршрутов создания команды или матча не означает, что формы создания доступны на сайте. API и UI нужно проверять раздельно.
- Исторические скриншоты PostgreSQL/Render нельзя использовать как доказательство конфигурации текущего `master`.
- Не добавлять скриншоты, логи или результаты, которые не были получены в ходе реальной проверки.

## Подход к тестированию

1. **Smoke:** проверить главную и основные API-маршруты.
2. **Функциональное тестирование:** пройти сценарии каталога, профиля, команд, матчей и LFG.
3. **Негативные проверки:** проверить валидацию, дубликаты, отсутствие авторизации и недостаточные права.
4. **Регрессия:** повторно проверить каталог после исправления JavaScript-селектора и Service Worker после исторической ошибки.
5. **Совместимость:** проверить адаптивность и клавиатурную навигацию.
6. **Проверка окружения:** установить, какой commit реально развёрнут и где хранятся данные.

## Правила фиксации результатов

Для каждого запуска указывать дату, commit, окружение, шаги, ожидаемый и фактический результат. Статусы Pass/Fail ставить только после выполнения проверки. Если результат известен только со слов пользователя, так и отмечать. Для дефектов сохранять доказательства, не раскрывая пароли, токены, cookies и значения секретных переменных.

## Критерии завершения

- Все приоритетные smoke/API-сценарии выполнены либо явно отмечены как заблокированные.
- Для каждого Fail заведён или обновлён баг-репорт.
- Исправленные дефекты повторно проверены.
- Матрица трассировки и отчёт о прогоне соответствуют фактическим результатам.
- Нет выдуманных доказательств и неподтверждённых утверждений о текущем деплое.
